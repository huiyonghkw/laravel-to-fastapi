EP07 · 迁移

把表结构变更交给版本管理

迁移就是「用代码描述数据库表结构的每一次改动，且能前进也能回退」。Laravel 用 artisan + 迁移文件；FastAPI 没有内置迁移，生态里用 Alembic 做同一件事。本篇对齐两者的心智。

01

一句话心智模型

无论是 php artisan make:migration 还是 alembic revision，本质都是「生成一份带序号的变更脚本，up 前进、down 回退」。Laravel 把它收进 database/migrations/；FastAPI 把 Alembic 配置放进 alembic/。同一套版本化思路，两种落笔。

Laravel 的迁移
  • artisan make:migration 生成带时间戳的文件
  • up() 建表 / 加字段，down() 逆向回退
  • php artisan migrate 按顺序执行
FastAPI 的迁移（Alembic）
  • alembic revision -m "..." 生成版本脚本
  • upgrade() 前进，downgrade() 回退
  • alembic upgrade head 跑到最新
一句话：Laravel 把迁移塞进框架，FastAPI 把迁移交给 Alembic。心智完全一致——脚本化、可回退、可多人协作。
02

对照①生成迁移文件

两边都先「生成一份空脚本」，再往里填表结构改动。左 Laravel 用 artisan；右 FastAPI 用 alembic 命令。

Laravel 13 · PHP
# 终端：生成迁移 php artisan make:migration \ create_posts_table # 生成 database/migrations/ # 2026_07_29_000001_create_posts_table.php return new class extends Migration { public function up(): void { Schema::create('posts', function ($t) { $t->id(); $t->string('title', 255); }); } public function down(): void { Schema::dropIfExists('posts'); } };
FastAPI 0.140 · Python
# 终端：生成迁移 alembic revision -m "create posts" # 生成 alembic/versions/ # xxxx_create_posts.py def upgrade(): op.create_table( "posts", sa.Column("id", sa.Integer(), primary_key=True), sa.Column("title", sa.String(255)), ) def downgrade(): op.drop_table("posts")
Laravel 的迁移文件自带 up()/down() 骨架且能直接用 Schema 流式建表；Alembic 的 upgrade()/downgrade() 用 op 指令，更贴近「SQL 操作原语」。
03

对照②一段完整的 Alembic 迁移脚本

这是 FastAPI 侧最贴近 Laravel 迁移的「实物」——一份可执行的 Alembic 版本脚本（取自 fastapi/app/ep07.py 的注释示例）。左边给 Laravel 的同构写法。

Laravel 13 · PHP
// database/migrations/ // 2026_07_29_..._create_posts_table.php public function up(): void { Schema::create('posts', function ($t) { $t->id(); $t->string('title', 255); $t->timestamps(); }); } public function down(): void { Schema::dropIfExists('posts'); }
FastAPI 0.140 · Python
# alembic/versions/xxxx_initial.py def upgrade(): op.create_table( "posts", sa.Column("id", sa.Integer(), primary_key=True), sa.Column("title", sa.String(255)), sa.Column("created_at", sa.DateTime(), nullable=True), ) def downgrade(): op.drop_table("posts")
两边都是「一个前进函数 + 一个回退函数」成对出现。回退函数不是可选项——它能让你 migrate:rollback / alembic downgrade -1 安全撤掉刚上的改动。
04

对照③执行迁移 vs 开发期一行建表

生产用迁移工具逐步跑；开发期 FastAPI 还能用 Base.metadata.create_all 一键建好所有表（ep07.py 的 /ep07/init 就是这么干的）。Laravel 没有等价「一行建表」，因为它依赖迁移文件。

Laravel 13 · PHP
# 执行全部待跑迁移 php artisan migrate # 回退最近一批 php artisan migrate:rollback # 重跑（开发期清库常用） php artisan migrate:fresh
FastAPI 0.140 · Python
# 生产：跑 Alembic 到最新 alembic upgrade head # 回退一步 alembic downgrade -1 # 开发期便捷：POST /ep07/init # 内部执行： Base.metadata.create_all(bind=engine) return {"tables": list(Base.metadata.tables.keys())}
create_all 只认当前 Base.metadata 里已导入的模型，不会补字段、不会删字段；它和迁移是两套机制，别在生产混用。
05

⚠️ Laravel 老手常见坑

坑 1 · create_all 只在开发用：它只能「建表」，改不了已有表结构、也不记录迁移历史。生产环境一律用 alembic upgrade head，否则数据库状态不可追溯。
坑 2 · 迁移要可逆：每个 upgrade() 都必须写对应的 downgrade()。只写前进不写回退，alembic downgrade 会直接报错，回滚就没了退路。
坑 3 · 忘了导入模型：Alembic 的 env.py 必须 import 你的模型模块，否则 autogenerate 看不到表、create_all 也建不出表。Laravel 反之——迁移文件本身就在描述结构，不受模型影响。

07

上手练习（10 分钟）

给 posts 表加一个 body 字段（text），两边各写一次「前进 + 回退」：

FastAPI · 你的练习
# alembic/versions/xxxx_add_body.py def upgrade(): op.add_column("posts", sa.Column("body", sa.Text(), nullable=True)) def downgrade(): op.drop_column("posts", "body") # 然后跑： alembic upgrade head
做完你会发现：add_column / drop_column 正好对上 Laravel 的 $table->text('body') 与回退里的删除。难点不在语法，在「养成每次改动都写可逆迁移」的习惯。
