EP13 · 异步与队列

响应先走，重活后台跑

「发邮件 / 写日志 / 跑报表」这种慢任务，不该卡住用户请求。Laravel 用 Queue 丢给 Worker；FastAPI 轻量的用 BackgroundTasks，重负载用 Celery / ARQ——心智完全一致。

01

一句话心智模型

两边都是「立即返回响应 + 把慢任务挪到后面跑」。差别只在「后面」是 Laravel 的独立 Worker 进程，还是 FastAPI 进程内的后台线程。重活一律交给真正的队列。

Laravel 的队列
  • dispatch(Job) / Queue::push 把任务入队
  • 独立 Worker 进程异步消费（php artisan queue:work）
  • 天生跨进程、可重试、可分布式
FastAPI 的异步
  • 轻量：BackgroundTasks 响应后同进程跑
  • 重活：Celery / ARQ + 独立 Worker，同 Laravel Queue
  • async def 还能把 I/O 等待让给事件循环
一句话：Laravel 队列 ≈ ARQ/Celery 队列；FastAPI 的 BackgroundTasks 只是「进程内小后台」，别把它当分布式队列用。
02

对照①把慢任务丢到后台

「立刻回 {queued:true}，邮件慢慢发」——左 Laravel 入队，右 FastAPI 加后台任务。

Laravel 13 · PHP
// routes/api.php Route::post('/notify', function (\Illuminate\Http\ Request $r) { \Illuminate\Support\Facades\Queue::push( new \App\Jobs\SendEmail( $r->input('email'))); return ['queued' => true, 'email' => $r->input('email')]; });
FastAPI 0.140 · Python
# fastapi/app/ep13.py @router.post('/notify') def notify(email: str, bg: BackgroundTasks): bg.add_task(_send_email, email) return {'queued': True, 'email': email}
Laravel 的 Queue::push 等价于 dispatch(new SendEmail(...))；FastAPI 用 BackgroundTasks 的 add_task 挂一个函数在响应后执行。两者都先返回、后干活。
03

对照②被后台执行的任务体

任务函数本身：左是 Laravel 的 Job 类（handle()），右是 FastAPI 的普通函数。

Laravel 13 · PHP
// app/Jobs/SendEmail.php class SendEmail implements \Illuminate\ Contracts\Queue\ShouldQueue { public function __construct( private string $email) {} public function handle() { // 发邮件 / 写日志，慢活 sleep(1); logger("sent to {$this->email}"); } }
FastAPI 0.140 · Python
# fastapi/app/ep13.py def _send_email(email: str): # 模拟耗时任务，响应返回后执行 time.sleep(0.1) print(f"sent email to {email}")
Laravel 的 Job 是类（可序列化进队列、可重试）；FastAPI 的 _send_email 只是个普通函数，只能在当前进程内跑。这正是「进程内 vs 跨进程」的分水岭。
04

对照③重负载：上真正的队列

邮件这种小活用 BackgroundTasks 够了；但「视频转码 / 批量推送 / 定时重算」必须跨进程。FastAPI 侧请出 Celery 或 ARQ，结构跟 Laravel Queue 一模一样。

Laravel Queue
  • dispatch(Job) 入队
  • Broker：Redis / DB / SQS
  • 消费：php artisan queue:work
  • 自带重试、失败表、延迟
FastAPI + ARQ / Celery
  • queue.enqueue(job) / await arq.redis.enqueue_job
  • Broker：Redis（ARQ）/ RabbitMQ（Celery）
  • 消费：独立 Worker 进程
  • 同样重试、延迟、并发
结论：把 FastAPI 的 BackgroundTasks 当成 Laravel 的「同步闭包」级别；要 Laravel Queue 那种能力，就直接上 ARQ/Celery，别硬扛。
05

⚠️ Laravel 老手常见坑

坑 1 · 把 BackgroundTasks 当分布式队列：它只在当前进程内跑，进程被 Gunicorn 回收、重启就丢任务。跨进程 / 必须不丢 → 用 Celery / ARQ。
坑 2 · 后台任务里写阻塞代码：骨架里用 time.sleep 只是示意。真实 I/O 请用 async def + await（如 httpx.AsyncClient），否则卡住整个事件循环，所有请求都慢。
坑 3 · 把 CPU 重活塞进 async：async def 只让「等待」不阻塞；纯 CPU 密集（转码/大循环）要用 run_in_threadpool 或丢队列，否则单进程被占满。

07

上手练习（10 分钟）

给 /ep13/notify 加一个「发完邮件再记一条审计日志」的第二步后台任务：

FastAPI · 你的练习
# 在 ep13.py 里追加： def _audit(email: str): print(f"audit: notified {email}") @router.post('/notify') def notify(email: str, bg: BackgroundTasks): bg.add_task(_send_email, email) bg.add_task(_audit, email) # 按顺序追加 return {'queued': True, 'email': email}
做完你会发现：add_task 按调用顺序排队，跟 Laravel Job 链（dispatch->withChain）一个心智。区别依旧是——它只在进程内，重活别这么干。
08

速查表（看完就能上手）

你想做LaravelFastAPI
轻量后台任务闭包 / 同步调用BackgroundTasks.add_task
入队异步任务dispatch(Job) / Queue::pushCelery / ARQ enqueue
任务体Job::handle()普通函数 / async 函数
消费进程queue:workWorker 进程（队列专用）

异步心智没变：
先返回响应，慢活往后挪。
